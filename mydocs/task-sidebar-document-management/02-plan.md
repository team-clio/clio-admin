# 사이드바 문서 관리 구현 계획

## 문서 목적

이 문서는 문서 관리 화면 재설계의 구현 순서와 사용자 결정 포인트를 정의한다.
결정되지 않은 항목은 구현하지 않으며, 각 결정은 `03-decisions.md`에 기록한다.

## 구현 원칙

- 기존 프로젝트 문서 API와 React Query 훅을 재사용한다.
- 문서 관리의 핵심 흐름을 업로드, 처리 상태 확인, 기존 문서 탐색 순서로 구성한다.
- 마우스 드래그 앤 드롭과 키보드 파일 선택을 같은 수준으로 지원한다.
- 데스크톱과 모바일에서 동일한 기능을 제공하되 화면 폭에 맞게 재배치한다.
- 기존 디자인 토큰과 공용 UI 컴포넌트를 우선 사용한다.

## 구현 단계

### 1. 내비게이션과 화면 경계 구성

- 문서 관리용 페이지 식별자와 사이드바 메뉴를 추가한다.
- 선택한 프로젝트 ID를 새 화면에 전달한다.
- 프로젝트 미선택 상태를 처리한다.
- 프로젝트 설정에 포함된 기존 문서 영역을 결정 결과에 따라 정리한다.

### 2. 문서 관리 레이아웃 재설계

- 페이지 헤더에 현재 프로젝트와 문서 관리 목적을 표시한다.
- 업로드 영역과 문서 목록의 정보 계층을 구성한다.
- 로딩, 빈 목록, 조회 오류 상태를 독립적으로 표현한다.
- 좁은 화면에서는 영역을 세로로 쌓고 파일 행의 정보를 축약한다.

### 3. 드래그 앤 드롭 업로드 구현

- 드래그 진입, 이탈, 드롭 상태를 시각적으로 구분한다.
- PDF와 Markdown 파일만 허용하고 잘못된 파일은 즉시 안내한다.
- 파일 선택 버튼과 숨겨진 파일 입력을 연결한다.
- 업로드 중 중복 조작을 막고 성공 후 목록을 갱신한다.
- 제목과 복수 파일 처리 방식은 결정 결과를 반영한다.

### 4. 파일 목록과 삭제 흐름 개선

- 파일명, 문서 제목, 생성 시각, 형식, 동기화 상태를 읽기 쉬운 행으로 표시한다.
- 동기화 중이거나 삭제 중인 항목의 조작 가능 상태를 구분한다.
- 기존 삭제 확인과 오류 피드백을 유지한다.
- 필요하면 목록 상단에 문서 수와 상태 요약을 표시한다.

### 5. 문서화와 검증

- 사이드바와 문서 화면 Storybook 사례를 갱신하거나 추가한다.
- 키보드 조작, 드롭 상태, 모바일 레이아웃을 브라우저에서 확인한다.
- `npm run typecheck`, `npm run lint`, `npm run build`를 실행한다.
- 변경된 UI와 API 매핑이 있다면 `API_UI_CHANGES.md`를 갱신한다.
- 결과와 검증 내용을 `04-result.md`에 기록한다.

## 사용자 결정 포인트

### D1. 사이드바 메뉴 위치와 이름

- 대안 A: `이슈 관리` 아래에 `프로젝트 문서`를 둔다.
  분석 업무와 가까워 접근성이 좋지만 이슈 메뉴의 의미가 넓어진다.
- 대안 B: 새 `프로젝트` 섹션을 만들고 `문서`와 `프로젝트 설정`을 함께 둔다.
  프로젝트 자원을 한곳에 모을 수 있지만 사이드바 구성이 한 단계 늘어난다.
- 대안 C: 기존 `설정` 아래에 `문서 관리`를 둔다.
  변경은 작지만 문서를 일상 업무보다 설정으로 인식하게 된다.
- 추천: 대안 B. 문서는 설정값이 아니라 프로젝트 분석 자원이므로 별도 프로젝트 섹션이 가장 명확하다.

### D2. 데스크톱 화면 레이아웃

- 대안 A: 상단 전체 폭 드롭존 아래에 전체 폭 파일 목록을 둔다.
  흐름이 단순하고 좁은 화면 전환이 자연스럽지만 긴 화면을 더 많이 스크롤한다.
- 대안 B: 왼쪽 넓은 파일 목록과 오른쪽 고정 업로드 패널의 2열로 구성한다.
  목록을 보면서 바로 업로드할 수 있지만 작은 노트북 화면에서는 각 열이 좁다.
- 대안 C: 작은 상단 업로드 도구 모음과 목록 중심 화면으로 구성한다.
  목록 탐색에는 유리하지만 드래그 앤 드롭 가능성이 덜 눈에 띈다.
- 추천: 대안 A. 업로드 후 결과를 바로 아래에서 확인하는 작업 순서가 명확하고 반응형 복잡도가 낮다.

### D3. 업로드 문서 제목 결정 방식

- 대안 A: 파일명에서 확장자를 제거해 제목을 자동 생성하고 별도 입력을 없앤다.
  업로드가 가장 빠르지만 사용자가 의미 있는 제목으로 다듬을 수 없다.
- 대안 B: 드롭 후 파일명 기반 제목을 미리 채운 검토 단계를 제공한다.
  제목을 수정할 수 있지만 업로드 전에 한 단계가 추가된다.
- 대안 C: 기존처럼 제목을 먼저 입력한 뒤 파일을 선택하거나 드롭한다.
  API와 잘 맞지만 드래그 앤 드롭의 간편함이 줄어든다.
- 추천: 대안 B. 기본값으로 빠르게 진행하면서 필요한 경우에만 제목을 고칠 수 있다.

### D4. 복수 파일 드롭 지원 범위

- 대안 A: 한 번에 한 파일만 허용한다.
  상태와 오류 처리가 단순하지만 여러 문서를 올릴 때 반복 작업이 필요하다.
- 대안 B: 여러 파일을 받고 기존 단일 업로드 API를 순차 호출한다.
  서버 변경 없이 편의성을 높이지만 일부 파일만 실패할 수 있어 개별 결과 표시가 필요하다.
- 대안 C: 서버에 일괄 업로드 API를 추가한다.
  원자적 처리를 설계할 수 있지만 이번 작업 범위가 서버까지 확대된다.
- 추천: 대안 B. 현재 API를 유지하면서 실제 드래그 앤 드롭 사용성을 가장 크게 개선한다.

### D5. 프로젝트 설정의 기존 문서 영역 처리

- 대안 A: 기존 영역을 제거하고 전용 화면으로 완전히 이전한다.
  중복이 없지만 기존 위치에 익숙한 사용자는 메뉴를 다시 찾아야 한다.
- 대안 B: 설정 화면에는 문서 수와 전용 화면 링크만 남긴다.
  기능 중복 없이 새 위치를 안내하지만 작은 요약 컴포넌트가 추가된다.
- 대안 C: 기존 관리 UI를 그대로 유지한다.
  기존 흐름을 보존하지만 관리 화면이 두 곳이 되어 유지보수와 사용자 기대가 갈린다.
- 추천: 대안 B. 전용 화면을 단일 관리 지점으로 유지하면서 이동 경로를 제공한다.

### D6. 업로드 성공·실패 피드백

- 대안 A: 드롭존 내부에 현재 작업 결과를 표시한다.
  맥락이 명확하지만 다음 업로드 때 이전 결과가 사라진다.
- 대안 B: 화면 상단 전역 알림만 표시한다.
  눈에 잘 띄지만 파일별 결과를 설명하기 어렵다.
- 대안 C: 드롭존에는 전체 진행 상태를, 대기 목록에는 파일별 결과를 표시한다.
  정보가 가장 명확하지만 상태 관리가 조금 늘어난다.
- 추천: 대안 C. 복수 파일의 부분 실패를 사용자가 정확히 확인하고 재시도할 수 있다.

## 검증 기준

- 선택된 프로젝트가 있을 때 목록 조회, 업로드, 삭제가 동작한다.
- 프로젝트가 없거나 선택되지 않은 상태에서 안전한 안내를 제공한다.
- 잘못된 형식과 복수 파일 부분 실패를 결정된 UX에 맞게 안내한다.
- 드롭존은 포인터와 키보드로 모두 사용할 수 있다.
- 데스크톱, 태블릿, 모바일 폭에서 핵심 조작이 가려지지 않는다.
- 타입 검사, ESLint, 프로덕션 빌드가 통과한다.
