# 사이드바 문서 관리 결정 기록

## 문서 목적

이 문서는 문서 관리 화면 재설계 과정에서 확정한 선택과 근거를 기록한다.

## D1. 사이드바 메뉴 위치와 이름

- 결정: 새 `프로젝트` 섹션을 만들고 `문서`와 `프로젝트 설정`을 함께 둔다.
- 근거: 문서는 설정값보다 프로젝트 분석에 사용하는 자원에 가깝다.
  프로젝트 단위 기능을 묶으면 사용자가 문서와 설정의 범위를 쉽게 이해할 수 있다.
- 제외: 이슈 관리 아래 배치는 섹션 의미를 넓히고, 설정 아래 배치는 일상적인 접근성을 낮춘다.

## D2. 데스크톱 화면 레이아웃

- 결정: 상단 전체 폭 드롭존 아래에 전체 폭 파일 목록을 둔다.
- 근거: 업로드 후 바로 아래 목록에서 처리 결과를 확인하는 작업 순서가 명확하다.
  같은 구조를 좁은 화면에서도 유지할 수 있어 반응형 동작을 예측하기 쉽다.
- 제외: 2열은 작은 노트북에서 목록과 업로드 영역이 좁고, 도구 모음형은 드롭 기능을 발견하기 어렵다.

## D3. 업로드 문서 제목 결정 방식

- 결정: 파일명에서 확장자를 제거한 제목을 기본값으로 제공하고 업로드 전에 수정할 수 있게 한다.
- 근거: 대부분은 자동 생성된 제목으로 빠르게 진행하고, 필요한 문서만 의미 있는 제목으로 다듬을 수 있다.
- 제외: 완전 자동 방식은 제목을 보정할 수 없고, 제목 선입력 방식은 드롭 업로드의 흐름을 끊는다.

## D4. 복수 파일 드롭 지원 범위

- 결정: 여러 파일을 받고 기존 단일 업로드 API를 순차 호출한다.
- 근거: 서버 변경 없이 여러 문서를 한 번에 준비할 수 있고 서버 부하와 결과 순서를 예측하기 쉽다.
- 제외: 단일 파일 제한은 반복 작업이 많고, 일괄 API 추가는 이번 프런트엔드 작업의 범위를 확대한다.

## D5. 프로젝트 설정의 기존 문서 영역 처리

- 결정: 기존 관리 UI를 제거하고 문서 수와 전용 화면으로 이동하는 링크만 남긴다.
- 근거: 관리 기능의 단일 진입점을 유지하면서 기존 위치를 찾는 사용자에게 새 위치를 안내할 수 있다.
- 제외: 완전 제거는 위치 변경 안내가 없고, 기존 UI 유지는 기능과 상태 관리가 중복된다.

## D6. 업로드 성공·실패 피드백

- 결정: 드롭존에는 전체 진행 상태를 표시하고 대기 목록에는 파일별 결과를 표시한다.
- 근거: 여러 파일 중 일부만 실패해도 해당 파일과 원인을 확인할 수 있고 전체 작업 진행 상황도 놓치지 않는다.
- 제외: 단일 영역이나 전역 알림만 사용하면 파일별 부분 실패와 재시도 대상을 설명하기 어렵다.
